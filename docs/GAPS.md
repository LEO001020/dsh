## The defect class this project kept producing

Three separate findings, all the same shape, all found by following the real
import graph rather than by reading module names:

| # | What was unwired | Consequence | Status |
|---|---|---|---|
| 1 | `WorkService.setLaunchPort` — zero production callers | the shipped profile could not launch a single child; every `submit` became `unknown` | FIXED, commit `2d4534f`, regression test `production-port.test.ts` |
| 2 | `WorkService.takeContinuation` — zero production callers | a managed run never disarmed the Goal round-driver, so TWO continuation owners could drive one root | FIXED, commit `982e82b`, result stored on the record |
| 3 | `recovery.ts` epoch guard — unreachable from production | the `epoch` field is inert; a cross-process stale generation is not refused | OPEN (G-SEAM-21) |

**The shared shape:** a mechanism is implemented, unit-tested, and correct — while
nothing in the product calls it. Every test passes because the test calls the
mechanism directly. This is the same failure as an oracle weaker than its
scenario, and it is the reason the launch-port and handover fixes each came with a
test that installs NOTHING.

**The standing check that finds it**, applied per module:

1. Build the import graph from the package's `exports` roots, not from a
   directory listing.
2. For each module, ask whether any NON-TEST importer reaches it.
3. If not, ask whether the product needs it. If yes, that is an unwired capability.
4. Write a test that exercises the PRODUCT path (a boot probe or a
   no-test-installed-seam test), because a direct-mount test cannot see this.
