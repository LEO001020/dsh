## 2. Where the connection file is written, with what mode, and where the key comes from

All line numbers are in the pinned Python environment
(`C:\Users\hzq00\AppData\Local\Programs\Python\Python314\Lib\site-packages\`),
jupyter_client **8.10.0**, ipykernel **7.3.0**, pyzmq **27.2.0**.

- **Written by** `jupyter_client/connect.py:55 write_connection_file`, called
  from `connect.py:532 ConnectionFileMixin.write_connection_file`, which the
  provisioner calls at `provisioning/local_provisioner.py:241-243`.
- **Path**: `connect.py:120-122` — when no name is given,
  `tempfile.mkstemp(".json")`, i.e. `%TEMP%\tmpXXXXXXXX.json`. Our code passes no
  name, so **the connection file lands in the system temp directory**, not in a
  per-session directory.
- **Mode**: `connect.py:185` wraps the write in `secure_write(fname)`, which is
  `jupyter_core/paths.py:1044`. On `os.name == "nt"` it creates the file with
  `os.open(fname, open_flag, 0o0600)` and then calls
  `win32_restrict_file_to_user(fname)` (`paths.py:1077-1080`, function at
  `paths.py:600`). **So the enforced permission is an ACL naming only the owning
  user**, and the measured ACL agrees.
- **Key**: generated by the provisioner at
  `provisioning/local_provisioner.py:229-232` — `zmq.curve_keypair()` when
  `km.curve_publickey is None`, with `transport_encryption='required'` from
  `manager.py:162`. The HMAC key itself is `cfg["key"] = key.decode()` at
  `connect.py:172`. Our broker requests the policy at `broker.py:379`
  (`KernelManager(transport_encryption="required")`) and **verifies the achieved
  result rather than the request**: `broker.py:423-431` re-reads the connection
  file and raises if `transport == "tcp"` without curve keys.

### Why `st_mode` is not the permission

Measured: a plainly created file in `%TEMP%` reports `st_mode` = `0o666` with
`S_IROTH` set. CPython on Windows synthesizes those bits from the read-only
attribute, so `0o666` means "an ordinary file", not "world-readable". The old gate
read `connection_file_world_readable: true` from that and asserted only
`connection_file_readable_by_owner`, which passed for the wrong reason.

**The gate now reads the ACL instead, with a control arm.** The same `icacls`
command is run on a file this test creates plainly, and the test asserts the two
readings **differ** — without that arm, a broken `icacls` invocation returning the
same string for both would look like a pass. The assertion is that no WORLD
principal (`Everyone`, `BUILTIN\Users`, `Authenticated Users`) appears in the
connection file's ACL.

`BUILTIN\Administrators:(F)` is **not** asserted against: it is the OS's own
elevation path, and this deployment's stated authority boundary is the OS user
account, not a sandbox. Claiming the file is unreadable by an administrator would
be a claim about Windows, not about this product.

## 3. The over-limit frame, in each direction

`MAX_FRAME_BYTES` is declared in two places that must agree: **`protocol.ts:41`**
(host) and **`broker.py:47`** (broker). Both are 4 MiB. The bound belongs to the
host↔broker CONTROL channel; it is not the kernel's ZMQ limit (§7).

### Direction A — host → broker (the encode direction)

`encodeFrame` (`protocol.ts:56-67`) refuses before producing any bytes.
Measured: `encodeRefused: true`, `bytesProducedOnRefusal: 0`. The byte count is
**measured, not hardcoded** — an earlier draft of the driver logged a literal `0`,
which is the "value logged as a measurement" defect round 1 caught.

### Direction B — broker → host (the decode direction)

`FrameDecoder.drain` (`protocol.ts:116-139`) refuses on the **declared length,
before buffering**. Measured with a 4-byte header claiming `MAX_FRAME_BYTES + 1`
and no payload: `decodeRefused: true`,
`decodeError: "declared frame length 4194305 exceeds the 4194304-byte limit"`,
`decodedFrameCount: 0`. A reader that trusted the prefix would block for bytes
that never arrive.

### Direction C — a frame that actually ARRIVES at the broker's read loop

This is a different code path from either above: `FrameReader.next_frame`
(`broker.py:98-108`) inside `main()`'s loop (`broker.py:952-980`). Measured by
writing a raw over-limit frame to the real control socket (the host's own encoder
refuses to build one, which is exactly what a peer without our bound does).

**Recovery half.** After both framing refusals, a normal cell still runs:
`after_over_limit_outcome: "ok"`, stdout `s6-ipy15-still-usable`, same epoch `1`.

**The delivered frame is refused by name and the broker tells the host.** The
refusal reaches the HOST's decoder, not just the broker's stderr:

```
host_transportRefusals: [{"code":"FRAME_TOO_LARGE",
  "detail":"declared frame length 4195328 exceeds the limit",
  "limitBytes":4194304,"declaredBytes":4195328}]
```

An event the host cannot decode is not a report — `asBrokerMessage` validates
every field and requires an integer `epoch` on every event, so the event carries
one (`broker.py frame_too_large_event`). The gate asserts both that a well-formed
refusal decodes **and** that one missing its `limitBytes` is REFUSED, so the check
cannot pass on a validator that accepts anything.

## 4. The three defects, with the before/after pair

The pair is archived: `before/transport-and-frame-bound.json` (captured with the
fixes reverted) vs `after/transport-and-frame-bound.json`. Same driver shape,
same stimulus.

| Reading | BEFORE | AFTER |
|---|---|---|
| `uncaughtExceptionCount` | **1** (`Error: write EOF`) | **0** |
| `cellAfterBrokerDeath_waitedMs` | **62005** (budget 62000) | **0** |
| `cellAfterBrokerDeath_errorMessage` | `broker did not answer execute within 62000 ms` | `the broker is not running: broker exited with code 2 signal null` |
| `shutdownOutcome` / `shutdown_waitedMs` | **hung** / 8012 | **resolved** / 0 |
| `unhandledRejectionCount` | **1** | **0** |
| `host_transportRefusals` | *(field did not exist)* | `[{code: FRAME_TOO_LARGE, limitBytes: 4194304, declaredBytes: 4195328}]` |

**D1 — the uncaught control-channel error.** `KernelHost` attached handlers to
stdout, stderr and the process exit, but nothing to `handle.control`. Node's
`EventEmitter` throws on an unhandled `'error'`, so the first write after the
broker exited killed the host process. Fixed by adding the listener
(`kernel.ts`, in `startInternal`).

**D2 — the 62 s wait.** `onProcessExit` rejects the entries that exist WHEN IT
FIRES, so a request issued afterwards registered a fresh entry nothing could
reject; its only escape was its own timer. The settlement time was **predicted
from the source before the run** — `cellTimeoutMs + interruptGraceMs + 60_000` =
62 000 ms — and measured at 62 005 ms and 62 017 ms across two runs. Fixed by
refusing immediately when `exitedDetail` is set (`kernel.ts`, `request`).

**D3 — the leaked pending entry and the hanging shutdown.** `request` registered
its pending entry and its timer, then encoded inside the `control.write(...)`
call. A refused encode threw with the entry already registered and its timer
armed; nothing removed it, and `shutdown`'s `failAll` later rejected it into no
handler. Fixed by encoding **before** registering, plus a `catch` around the
write so a synchronous write failure cannot leak its entry either
(`kernel.ts`, `request`).

## 7. Product reachability

`KernelHost` is constructed at **`kernel-plugin.ts:515-533`** inside
`KernelService.entryFor`, which is the creation transaction for a Session's
kernel. `entryFor` is reached from `runCell` (`kernel-plugin.ts:580`), which is
the body behind the model-facing `ipython` tool (`ipython-tool.ts:237`). The
broker is spawned through `ctx.subprocess`, the profile's real subprocess
service.

So the path is: **model calls `ipython` → `KernelService.runCell` → `entryFor` →
`KernelHost` → control channel → `broker.py`.** Every fix in this slice is on that
path. The boot that reaches it is the daily profile
(`cordis.patch.yml:69` sets `outputCapBytes: 262144`).

**What is NOT claimed:** the `FRAME_TOO_LARGE` refusal was exercised by writing a
raw frame to the live control socket, which is a fault injection on a real
transport, not a model action. No model-facing path produces an over-limit
control frame today, because `encodeFrame` refuses to build one — the injection
stands in for a peer that does not share our bound.

## 8. Claims I am not making

1. **Not** claiming the transport is secure in general. The specific facts
   measured are: TCP, CurveZMQ keys present, no plaintext warning, ACL naming
   only the owner and Administrators. Nothing here establishes confidentiality
   against a same-user attacker, and nothing here audits the kernel's own ZMQ
   sockets.
2. **Not** claiming the kernel's ZMQ message size is bounded. Measured:
   libzmq's `MAXMSGSIZE` default is **-1 (no limit)** and jupyter_client never
   sets it (0 occurrences across `jupyter_client/` and `ipykernel/`). The 4 MiB
   bound is the host↔broker control channel's, and it does not constrain what a
   cell can send over IOPub. That is a **separate, unmeasured exposure**, recorded
   here rather than folded into this slice.
3. **Not** claiming the connection file is in a per-session directory. It is
   `%TEMP%\tmpXXXXXXXX.json` — shared temp space, protected by ACL, not by
   location.
4. **Not** claiming the broker's exit on an over-limit frame is wrong. A frame
   whose declared length exceeds the bound leaves no trustworthy next boundary, so
   abandoning the stream is correct; what was wrong was doing it **silently**.
5. **Not** claiming `droppedFrames` is now populated. It is still structurally 0
   and the gate still pins that. The v2 decision (D2) removed the requirement; the
   structured refusal replaces it.
6. **Not** claiming the host recovers the kernel after the broker dies. The next
   cell is refused promptly and correctly; starting a new kernel is a lifecycle
   decision outside this slice and was not measured.
7. **Not** claiming `BUILTIN\Administrators:(F)` on the connection file is a
   defect. It is stated as a fact, not as a finding.
