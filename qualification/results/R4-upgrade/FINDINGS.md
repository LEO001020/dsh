## 2. UPG-06 — the decision, with its justification

### 2.1 The sweep is age-based, established from source

`SweepOptions` — `D:\DSH\src\dsh-src\packages\spill\spill-local\src\cleanup.ts:173-184`:

```ts
/** Options for {@link sweepSpillRoots} — the roots to scan, the age cutoff, and a failure sink. */
export interface SweepOptions {
  /** Roots to sweep (configured/active root and/or discovered prior-default roots). */
  roots: SweepRoot[]
  /**
   * Epoch-millis cutoff: a regular file is deleted when its `mtime` is strictly
   * older than this. The caller derives it from `now - cleanupPeriodDays`, so a
   * file written exactly at the boundary is kept (only strictly-older expires).
   */
  cutoffMs: number
  /** Where a contained filesystem failure is reported; the sweep itself never throws. */
  warn: WarnFn
}
```

Three fields: `roots`, `cutoffMs`, `warn`. **No reference, lease, live-session or pin input of any
kind.** The deletion decision is two lines — `cleanup.ts:255-257`:

```ts
if (!stats.isFile()) continue
if (stats.mtimeMs >= cutoffMs) continue
await unlinkIdempotent(path, warn)
```

and the cutoff is derived purely from a config number, `index.ts:114`:
`const cutoffMs = Date.now() - this.config.cleanupPeriodDays * MS_PER_DAY` (default 30 days,
`index.ts:68`). So a still-referenced spill artifact older than the cutoff **is deleted**, and the
sweep cannot do otherwise — this is not a misconfiguration.

### 2.2 The other collector is correct, and unreachable

`LocalArtifactStore.collectGarbage` — `src/artifacts.ts:434` — takes exactly the reference input the
spill sweep lacks:

```ts
async collectGarbage(
  referenced: ReadonlySet<string>,
  graceMs: number,
  now: number = Date.now(),
): Promise<{ collected: string[]; skipped: Array<{ artifact: string; reason: string }> }>
```

with `artifacts.ts:459-465`:

```ts
if (referenced.has(artifact)) {
  skipped.push({ artifact, reason: 'referenced' })
  continue
}
if (this.pinned.has(artifact)) {
  skipped.push({ artifact, reason: 'pinned' })
  continue
}
```

This is the right shape. **It has no production caller.** `DataPlaneService` — the host service the
shipped profile actually mounts (`cordis.patch.yml`, row `daily-data-plane`) — exposes
`reconcile()` (`data-service.ts:357`), which only *reports* orphans, and exposes no collection entry
point at all. Every `collectGarbage` call site in the package is a test.

### 2.3 The two honest options, and why neither is taken here

**(a) Give the spill sweep a reference input — NOT AVAILABLE, because there is no real liveness
source, and inventing one is forbidden.**

The spill seam is `saveText` and nothing else. `packages/spill/spill/src/index.ts`:

> The Service Definition is deliberately minimal: `saveText` and nothing else.

and its own module doc says the locator is opaque with no unified read/delete/ACL/refcount contract.
There is no `open`, no `stat`, no range read, no delete — therefore no refcount and no lease. The
locator is not persisted anywhere this project owns, so a sweep has nothing to consult. Adding a
"live session set" parameter inside the sweep would be *inventing the liveness source*: it would
make a test green while the product still had no such source. That is exactly the move this task
forbids, so I did not make it.

**(b) Wire the artifact store's real collector to a production caller — ACHIEVABLE, and the correct
fix, but the caller is not in a file I own.** The exact patch I want is in §5 below. It belongs in
`data-service.ts` / `data-plugin.ts`, which are owned by another agent, and the only durable
reference source is `StorageReferenceLog`, a class *inside* `data-service.ts`.

## 3. The three PASSes, re-verified by reading the assertions

### UPG-03 — was the oracle weaker than the claim? YES, and it is now fixed.

**Before:** one foreign directory (`session-backup`) was asserted to survive, and the exact-shape
rule was *also* asserted by regexing `SESSION_DIR_RE` out of the source. A single near-miss is not
"exact shape", and a shape rule read out of the source is a statement about code text, not about
behaviour — a regression that loosened the regex to `^session-[0-9a-f]{11,13}$` would have kept that
test green while sweeping 11- and 13-character names.

**Now (new case):** the boundary is planted as a *family* and survival is observed by file content:

| planted name | why it is a boundary |
|---|---|
| `session-0123456789a` | 11 hex chars (one short) |
| `session-0123456789abc` | 13 hex chars (one long) |
| `session-ABCDEF123456` | 12 chars but uppercase — `[0-9a-f]` is case-sensitive |
| `session-0123456789az` | 12 chars, one outside the hex alphabet |
| `session-` | the bare prefix |
| `session-backup` | the prefix-based-regression hazard |
| `session-0123456789ab-extra` | the `startsWith`-regression hazard |

plus a **positive control** (an in-shape `session-<12hex>` directory with an expired file, which MUST
be reclaimed — otherwise the test proves nothing) and a **session-shaped junction** pointing at a
foreign tree, with `lstatSync(link).isSymbolicLink() === true` asserted as the premise. All seven
near-misses survive byte-identical, the foreign tree behind the junction is untouched, the junction
itself still exists, and the sweep *reported* `skipped unsafe session directory`.

The permissions case is unchanged and honest about its own limit: the POSIX mode is asserted from
the source's declared `0o700`/`0o600` (`store.ts`), because Windows has no meaningful mode bits.

### UPG-04 — was the oracle weaker than the claim? Partly, and it is now fixed.

The case did copy a real store (`cpSync`), reopen it in a fresh host over a different directory, and
compare `hashTree(source)` to `hashTree(destination)` — a genuine recursive sha256 map, so the core
claim was sound. Two things were weaker than the claim:

- The digest was never *named*: identity was only ever a map equality.
- Byte-identity was checked **before** the reopen and never after. A reopen that re-serialized the
  document — same semantics, different bytes — would have broken "byte-identical" silently.

**Now:** a real `createHash('sha256')` of the store file is computed and asserted to be 64 hex
characters, the destination's digest is asserted equal to it, and **both `hashTree(destination)` and
the file digest are re-asserted after the reopen**. The source is still asserted unchanged.

### UPG-05 — was the oracle weaker than the claim? Partly, and it is now fixed.

The refusal itself was already strong: `StorageError` with code `version-mismatch`, thrown by the
backend rather than the domain, and a control showing the same directory opens once the version is
restored. Two gaps:

- "bytes untouched" was a **string** comparison (`toBe(mutated)`), not a digest — it happens to imply
  byte equality, but the claim is about bytes and the evidence file records digests.
- Nothing checked that the refused open wrote no **side file** (a temp file, a journal, a backup) —
  i.e. "the store file is intact" was checked, but not "the medium was not touched".

**Now:** the mutated bytes are hashed, the digest is asserted different from the original's, and
after the refusal both the digest and `readdirSync(dir)` (asserted to be exactly `[STORE_FILE]`) are
checked.

## 4. The rollback rehearsal, and the rollback semantics

### 4.1 `u06-rollback.mjs` exists, runs, and is honest about being a rehearsal

It exists at `qualification/results/M9.20-real-tasks/u06-rollback.mjs` (471 lines), it is executable,
and **I ran it myself**: exit 0, `summary {"pass":12,"fail":0}`, report re-written to
`qualification/results/R4-upgrade/u06-rollback-rerun.json`. I did not take the claim from the notes.

**Is its claim about a rehearsal, and does it say so? Yes, on both counts, and the wording is
sound.** Its `kind` is `ROLLBACK_REHEARSAL_OVER_A_TEMP_HOME`; its header carries a `WHAT IS REAL AND
WHAT IS A FIXTURE` section; its final step R11 records the fixtures in the report itself
("the 'new version' is a copy of the same built artifact with a version bumped… The remote is a
counting in-process fake… the rehearsal is about the PROCEDURE, not about a real upgrade"); and its
top-level `notClaimed` array names both limits. The finding does **not** read as though a real remote
was exercised.

**What I added** so this cannot rot into a header sentence: a new case reads the rehearsal's *own
report* and requires the counter as a **number** — `remoteStillHoldsEffect === true` (R9),
`performCountBeforeReconcile === 1` and `performCountAfterReconcile === 1` with
`performedByCall === false` (R8) — plus `notClaimed` containing "the remote is a counting in-process
fake". A claim in a header is not a measurement; this is.

### 4.2 Does anything exercise a REAL two-version rollback? Before this work: **NO. That was a real
gap, and I built one.**

The gap was real. `docs/RECOVERY.md` claims "Rollback restores old artifacts **and** the old
consistent state snapshot", and `docs/OPERATIONS.md` repeats it. But:

- the UPG-04 case copies **one** store with **one** version of the code — the same binary writes and
  reads;
- `durability-advanced.test.ts` D12 **hand-edits** a stored record to *look* foreign (`record['version'] = 2`),
  which is a shape rejection, not a rollback;
- `u06-rollback.mjs` stages an old artifact as a *directory copy* and rewinds a *JSON fixture* — the
  procedure is rehearsed, but no domain-layer read/write crosses two schema versions.

**The new case** (`UPG-05: a REAL two-version rollback`) runs three real generations over one
directory:

- **v1 writes** — the *production* spec (`WORK_SCHEMA_VERSION`, `single` layout) over a real
  `WorkService`, so the v1 store is production-shaped.
- **v2 opens** — a real domain at version 2, `layout: 'per-record'`, `compatibleVersions: [1]`. This
  is the checkout's own documented upgrade path (`storage-domain/src/spec.ts:48-56`: a
  `compatibleVersions` entry is what lets the backend read a legacy whole-unit file for the one-time
  bootstrap). It reads the v1 record, **migrates** it, and writes records stamped 2.- **v1 opens** — the same directory with the version-1 spec. **The rollback.**

**The measured finding, asserted:** the rolled-back v1 build sees an **EMPTY table**. Both records
the v2 build wrote are stamped 2, a version-1 reader accepts only stamp 1, and the per-record
contract *discards* an unaccepted record document rather than migrating it
(`storage-json/src/format.ts:105-111`, `per-record-unit.ts:14-16`). The bytes are still on disk — the
data was not deleted, it became **unreadable**. The test asserts both halves: `keys()` is `[]` while
both `.json` documents still exist. That is the concrete, silent data-loss shape the docs' "restore
the snapshot **too**" sentence exists for, and it is now measured rather than asserted. The case
then performs the prescribed recovery (the v2 tree is removed; the pre-upgrade store file, whose
digest is asserted unchanged, is what v1 reads) and confirms the run comes back.

**The other direction is measured too:** a v1 `single` reader over a v2-written `single` unit is
**refused** with `StorageError/version-mismatch` and the newer bytes are left alone. Both directions
fail; they differ in *how* — the per-record one fails silently, the single one loudly. A rollback
procedure needs to know that difference.

**Honest limit of the new case, stated in the test itself:** the two "versions" are domain specs
built in-process from the production schema — a real version-2 *spec*, but not a separately installed
artifact. `u06-rollback.mjs` supplies the staged-artifact half; this case supplies the half that
rehearsal cannot, a real domain-layer read/write across two schema versions over one store directory.

## 5. The patch I want for UPG-06 — NOT applied

`data-service.ts`, `DataPlaneService` — add a method beside `reconcile()` (line 357):

```ts
  /**
   * Reclaim unreferenced objects, respecting every committed reference and every
   * pin. This is the production caller `LocalArtifactStore.collectGarbage` has
   * never had: without it, UPG-06's property holds only because nothing collects.
   *
   * `referencedArtifacts()` reads the DURABLE reference table, so a live
   * reference survives a restart. The grace window is required, not optional: a
   * crash between "object published" and "reference committed" leaves an object
   * whose referencing event may still be in flight, and collecting it
   * immediately would turn a recoverable orphan into an integrity error.
   */
  async collectGarbage(graceMs: number, now?: number) {
    const log = this.requireLog()
    return await this.store.collectGarbage(await log.referencedArtifacts(), graceMs, now)
  }
```

`data-plugin.ts` — call it on activation, after `service.open(...)`, with the grace window as
configuration rather than a constant:

```ts
  // One best-effort GC pass after the reference table is open. Best-effort for the
  // same reason the spill sweep is: a GC failure must not fail activation.
  ctx.effect(() => () => service.close(), 'dsh-daily-data: reference domain')
  await service.open(ctx.storageDomain)
  await service.collectGarbage(config.gcGraceMs ?? 24 * 60 * 60 * 1000).catch(error => {
    ctx.logger.warn(`dailyData: startup GC failed: ${String(error)}`)
  })
```

`DataServiceConfig` gains `gcGraceMs?: number`. With that in place the UPG-06 import-graph case
(test 5 above) goes red by design, which is the signal that the gate is now closable — and the

## 7. Two defects found in the cited evidence (reported, not fixed)

Both are in `qualification/results/M9.20-real-tasks/u06-rollback.mjs`, which I do not own. Raw
reproduction: `qualification/results/R4-upgrade/u06-fixture-defect.txt` (exit 0).

### 7.1 The fixture adapter returns the wrong discriminator, so R3 passed on `undefined`

The rehearsal's fake remote (`u06-rollback.mjs:246-259`) returns
`{ kind: 'accepted', resultRef: \`remote-${n}\` }`. But `EffectPerformResult`
(`src/effects.ts:253-256`) is discriminated on **`status`**, not `kind`:

```ts
export type EffectPerformResult =
  | { readonly status: 'confirmed'; readonly resultRef: string; readonly remoteKey?: string; readonly detail?: string }
  | { readonly status: 'not_started'; readonly detail: string }
  | { readonly status: 'unknown'; readonly detail: string }
```

I reproduced this: `ledger.perform(adapter, intent)` returns `outcome: undefined`,
`resultRef: undefined`, and writes a record whose `status` field is **absent** — so the stored
document fails `effectRecordSchema` at reopen. The rehearsal's R3 still reports PASS because its
check is `performed.performed ? 'PASS' : 'FAIL'`, which is true even when the outcome is `undefined`.
**With `status: 'confirmed'` instead of `kind: 'accepted'`, the same sequence works end to end.**

### 7.2 R8a's "rewound ledger" refusal is the fixture defect, not the schema guard

R8a reports the ledger refusing to open over rewound state, and the script's prose concludes that
"a state rewind destroys the LOCAL knowledge of an effect while the REMOTE effect survives". But the
effect store is a **separate directory** (`u06-rollback.mjs:229-230`, `join(work, 'effect-store')`)
that the rewind at lines 300-302 never touches. The refusal R8a observes is caused by 7.1 — a
`status`-less record written by the broken fixture — not by a rewind. I measured both:

- with the **broken** fixture: the record has no `status`, reopen is refused with
  `DomainError/invalid-record`, exactly as R8a reports;
- with the **corrected** fixture: the record has `status: 'confirmed'`, reopen **succeeds**, and the
  real `EffectLedger.reconcile` returns `confirmed` with `performed: false` and the remote's
  `perform` count unchanged at 1 — which is the stronger, intended demonstration of "reconcile, never
  replay".

Separately, when the effect ledger genuinely *does* live in the rewound tree, the outcome is not a
refusal at all: the ledger opens cleanly with **zero** operations, so the local knowledge of the
effect is **silently gone** while the remote still holds it. That is a sharper and more alarming
statement than R8a's, and it is the one a rollback procedure should be written against. Neither the
script's prose nor its report currently says it.

I did not edit the script — it is outside my ownership. Both defects are recorded here so the UPG-05
citation is not read as stronger than it is.
