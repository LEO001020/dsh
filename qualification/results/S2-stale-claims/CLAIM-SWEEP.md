# S2 — the whole-repo claim sweep, and how each hit was classified

The brief required searching the WHOLE repo (excluding `node_modules` and the
pinned checkout) for surviving claims of the epoch/settlement/recovery guarantee,
and reporting any site R9's list of nine did not contain.

## Method

`claim-sweep.py` walks every file under the repository root except `node_modules`,
`.git`, `lib`, `dist`, `coverage`, and R9's own evidence directory (which
legitimately documents the deletion), and reports `file:line` plus an excerpt for
eight claim patterns:

| Pattern | Why it is in the list |
|---|---|
| `applyWorkerSettlement`, `WorkerSettlement`, `RefusalLedger` | the deleted symbols by name |
| `dsh_daily_work_refusals` | the deleted domain |
| `run\s*epoch` / `run-epoch` / `run epoch` | the claim in prose |
| `stale[- ]epoch`, `stale generation`, `superseded generation`, `被取代世代` | the claim in its guarantee form |
| `settlement` | the mechanism |
| `INV-L3` | the invariant that stated it |

`epoch` alone is deliberately NOT a pattern: it is too broad, because
`kernel-lifecycle.ts` and `history-plane.ts` carry the KERNEL epoch, a different
field that shares the word (G-SEAM-43). A sweep that counted those would report
the conflation as if it were the defect.

Re-run with `python qualification/results/S2-stale-claims/claim-sweep.py`.

## Classification of the hits

Every hit falls into exactly one of five classes. The class decides what happens
to it, and the classes are the point of this file — the raw output was 135 KB of
`file:line` excerpts and is not reproduced here.

### Class A — CORRECTED IN THIS SLICE (the sites I own)

R9's nine, plus the two sites R9 did not list. Enumerated in `FINDINGS.md` §1 and
§2, and in the slice report's `WHAT CHANGED`. Re-running the sweep after the
corrections shows these sites still matching the patterns — **by design**: the
corrections *name* the deleted machinery in order to record what was removed and
why. A sweep that returned zero hits here would mean the documentation had been
silently erased, which is the outcome the brief forbids.

### Class B — HISTORICAL EVIDENCE, CORRECTLY LEFT ALONE

`qualification/results/**` — M9.6, M9.11, M9.15, M9.21, M10-shrink, P3-security,
R3-unwired, R10-security, T9-recovery, T16-docs, V6-recovery, M-DEP-SEC-UPG,
MAIN-112-status, R9-delivery, and the `P1-suite-triage` / `M*.txt` test logs.

These are **measurements taken at a named commit**, and several of them
(`M9.11-tool-protocol/FINDINGS.md:114-128`, `M9.6-cost/FINDINGS.md:224-232`,
`M10-shrink/FINDINGS.md:297-337`, `R10-security/FINDINGS.md:263,286,323,487`)
describe the guard as existing **because it did exist when they were written**.

**They must not be edited.** Rewriting a measurement to match a later tree
destroys the audit trail — it would make the record unable to show that the guard
once existed, which is exactly what the REC-09/REC-10 FAILs rest on. The
correction belongs in the current documents, which is where it was made.

This is the same rule the project already applies to the frozen spec: v1's
contradictory oracles stay contradictory on purpose.

### Class C — A VERDICT ARTIFACT, REPORTED RATHER THAN EDITED

`qualification/results/M-DEP-SEC-UPG/UPG-08-verdict.txt` is regenerated by
`upg-gates.test.ts` on every run, so its SEC-06 line updated itself when the test
was corrected. I staged that one file because it is a **derived** artifact whose
generator I changed — leaving it stale would make the test suite's own output
disagree with the test.

Two neighbours in the same directory (`declared-vs-imported.txt`,
`typecheck-errors.txt`) were ALSO regenerated by running `dep-gates.test.ts`, but
their diffs are unrelated to this slice (they pick up sibling round-1 work and a
new timestamp). **I reverted both** rather than sweep them into my commit.

### Class D — LIVE TOOLING, REPORTED NOT CHANGED

`qualification/runners/file-result.py:424` — the `--vocabulary-test` topology
string reads *"`applyWorkerSettlement` has no production caller"*.

Not changed, and not false: a deleted function also has no caller, so the sentence
is still true. It is stale in the sense that it names the wrong REASON. It is a
live runner whose self-test asserts that string, and its subject is the
`NOT_CLAIMED` vocabulary, not the mechanism — editing it is a change to
qualification tooling rather than to a claim about the product. **Flagged here for
the root agent.**

### Class E — OUTSIDE MY FILE LIST

| Site | Stale how |
|---|---|
| `docs/decisions/TRUSTED-LOCAL-SPEC.md:71,171` | cites "85 PASSes in `qualification/gates.json`"; now 84 |
| `docs/decisions/AUDIT-REQUEST-nosandbox.md:37` | cites the 127-reference integrity check; now 125 |
| `compatibility.lock.json` `decision_reason` | names `G-SEAM-21 (epoch guard unreachable)` as one of the 13 FAILs, and describes the guard as a mechanism that "works with nothing in the product that calls it" — it is now deleted rather than caller-less. **Not edited: the file is explicitly out of my ownership.** |
| `docs/GAPS.md` structure | duplicate finding numbers, inconsistent status vocabulary — **writer S14's slice**, per the root agent's boundary |

## What the sweep does NOT establish

1. **It is a text sweep, not a semantic one.** A claim of the guarantee phrased
   without any of these words would not be found. It is a completeness aid, not a
   proof of completeness.
2. **It does not decide truth.** Every hit is classified by reading it. The sweep
   found the SITES; the tree measurement (`probe.py`) decided what is TRUE at each.
3. **It does not audit the other 103 gate rows' notes.** Only D10's note was
   re-judged against the tree, because only D10's named a mechanism this slice
   measured. See the slice report's `UNRESOLVED`.
